01 · The decision

What default time limit should an unattended agent task get?

If I were the PM for agent tasks in scheduled jobs: the agent now runs with no human watching and auto-approval on. Most runs wrap up in a few minutes, but some investigations legitimately take half an hour, and a small share get stuck in a loop and never finish. The default duration limit decides who gets hurt: too short and we kill good work; too long and a stuck agent blocks the morning pipeline and burns compute.

Customer problem

“My 7am job hung until noon.”

A data engineer schedules a nightly anomaly-triage agent after the load job. One night the agent loops on a flaky tool call. Nothing alerts, downstream dashboards stay stale, and the bill shows five idle agent-hours. The next week she adds her own 5-minute timeout, and now her longer audits get cut off mid-answer.

Proposed change

Ship a smart default duration limit

Every new agent task gets a default timeout (editable), plus an optional single automatic retry on timeout. The prototype below picks the number.

Success metric

Delivered-answer rate ≥ 97%

Share of scheduled agent runs that end with a final response the downstream task can use, within the job's window.

04 · The math

The math, from my Monte Carlo course

Inverse CDF method. Any distribution has a cumulative curve F that climbs from 0 to 1. Draw a uniform U between 0 and 1, read it on the vertical axis, and walk across to the curve: the x you land on, F⁻¹(U), is a draw from that distribution. One uniform in, one realistic sample out.

step time (exponential): T = −μ · ln(U)
tool steps (geometric): K = ⌈ ln(U) / ln(1−p) ⌉
task type (discrete): first k with U ≤ F(k)

Product example. “How long does one tool call take?” is exponential: most are quick, a few drag. “How many tool calls before the agent is done?” is geometric: after each step there's a chance p it has enough to answer. The task type is a finite table, so I cut [0,1] into slices sized by each type's share and see which slice U falls in (the bar on the right). Stack them and I get a whole run's duration without ever writing its messy distribution down.

Why Monte Carlo. The total runtime is a random sum of random step times, plus a stuck-loop mixture. The kill rate at a limit t is just the fraction of simulated healthy runs longer than t, and by the law of large numbers that fraction settles on the truth as runs grow (its standard error shrinks like 1/√n).

05 · Real data

How I'd run it on real data

SQL · fit the inputs from run history

-- illustrative table names
WITH runs AS (
  SELECT task_kind,
         run_id,
         tool_steps,
         duration_s,
         end_state            -- 'SUCCESS' | 'TIMEOUT' | 'CANCELED'
  FROM main.agent_ops.agent_task_runs
  WHERE start_time >= current_date() - INTERVAL 30 DAYS
)
SELECT task_kind,
       count(*) / sum(count(*)) OVER ()      AS share,
       1 / avg(tool_steps)                   AS p_stop,
       avg(duration_s / tool_steps)          AS mean_step_s,
       avg(CASE WHEN end_state = 'TIMEOUT'
                 AND tool_steps > 150 THEN 1 ELSE 0 END) AS loop_rate,
       percentile_approx(duration_s, 0.95)   AS p95_s
FROM runs
GROUP BY task_kind;

Python · inverse-CDF simulation

import numpy as np
rng = np.random.default_rng(102)

def simulate(kinds, n=20_000, loop_rate=0.02):
    share = kinds["share"].to_numpy()
    k = np.searchsorted(np.cumsum(share), rng.random(n))
    p = kinds["p_stop"].to_numpy()[k]
    mu = kinds["mean_step_s"].to_numpy()[k]
    steps = np.ceil(np.log(rng.random(n)) / np.log1p(-p))
    # sum of K exponentials, each -mu*ln(U)
    dur = np.array([(-m*np.log(rng.random(int(s)))).sum()
                    for m, s in zip(mu, steps)]) + 20
    stuck = rng.random(n) < loop_rate
    dur[stuck] = np.inf
    return k, dur, stuck

def kill_rate(dur, stuck, limit_s):
    return (dur[~stuck] > limit_s).mean()

k, dur, stuck = simulate(kinds)
best = min(t for t in range(120, 3601, 60)
           if kill_rate(dur, stuck, t) <= 0.02)
